# R-извлечение и E/C-коррекция на caniculus

**Статус: подготовка, новый прогон не запущен.** Эта процедура относится ко всем 750 размеченным ответам, первичному R-извлечению и четырём условиям коррекции `B`, `E`, `C`, `EC`. Прежний QA100 с 12 условиями описан отдельно в [исторической записи](history/qa100-20260919.md). Его разрешение на серверный запуск не распространяется на новый прогон. Перед планированием передачи файлов, Docker, GPU или запуска прочитать [правила сервера](server-resource-rules.md); для исполнения нужна отдельная команда владельца.

## Зафиксированный дизайн

- Выборка — все 750 доступных размеченных ответов из закреплённого CSV: 599 train и 151 test по прежнему фиксированному split. Метки GPT-4o и split не выбирают ID и не оценивают исправления. CLI проверяет SHA-256 точных source JSONL и answer CSV и хеш списка 750 ID. Источников QA всего 989; 239 без ответа в этот прогон не входят.
- Сначала `extract-r` один раз извлекает KGGen-тройки для контекста, вопроса и исходного ответа каждого из 750 ID. Отдельной Gemini-проверки R нет. Сохраняются 750 закрытых source-артефактов и KG-кэш. R не становится условием коррекции и не попадает в её промпты. После завершения этого этапа E читает уже извлечённые графы в режиме `cache_only`; повторный вызов KGGen запрещён.
- Каждый ответ независимо исправляется с исходного текста за одну итерацию: `B` видит вопрос, evidence и ответ; `E` дополнительно видит диагностику сущностей; `C` — клеймы VeriScore с четырёхклассовой проверкой Gemini (`veriscore.claim_verifier.labels: critical`, настройки `critical.claim_verifier`, протокол кэша `det-rep-four-way-verdict-v2`); `EC` — оба блока. VeriScore-клеймы не отбираются по наличию entity.
- Все условия используют одинаковые исходные данные, evidence, Llama checkpoint, параметры генерации и prompt-основу. Gemini готовит только нужные E и C отдельно; сбой одного компонента фиксируется с типом и не превращается в успешный результат другого. `B` не требует Gemini.
- Ожидаемый объём полного прогона — **750 R-артефактов и 750 × 4 = 3000 траекторий**. Ни код, ни запуск не вычисляют оценку качества исправлений. Независимый evaluator и ручной аудит принадлежат другой команде.

## Подготовка отдельного запуска

Новые каталоги R, коррекции и кэша разместить вне репозитория в личной области `/mnt/ssd/a.maslov` с закрытыми правами. Не использовать каталог, кэши или результаты `qa100-20260919`. Входные `source_info.jsonl` и CSV, полный input manifest, код/образ, `config.example.yaml`, Gemini gateway revision, снимок S-BERT и точный commit весов Llama должны быть проверены и закреплены до первого запроса. Изменение любого из них, seed, числа итераций или списка условий требует нового каталога запуска; возобновлять можно только неизменный запуск.

На caniculus научный Python исполняется только в Docker без root. Для этого прогона `Dockerfile.experiment` собирает один контейнер с изолированным Python-окружением эксперимента и закреплённым vLLM. Контейнеру передаётся только GPU 2 по её актуально проверенному UUID. Во время R-этапа процесс vLLM не работает и GPU не используется научным кодом; после проверки полного R-этапа vLLM запускается как отдельный процесс внутри того же контейнера, затем выполняется коррекция. Входы и веса монтируются только на чтение, рабочий каталог — с личного SSD, поэтому остановка или удаление контейнера не уничтожает checkpoint. Перед запуском повторно проверить владельца рабочей области, свободное место, Docker, загрузку GPU и процессы; согласовать время и предупредить коллег согласно [правилам](server-resource-rules.md). Контрольные версии и UUID, записанные в сентябре, могут измениться; их значения в [истории QA100](history/qa100-20260919.md) не заменяют новую проверку. Не затрагивать чужие файлы, контейнеры или процессы.

Когда владелец отдельно разрешит запуск, выполнить стадии по порядку:

1. Подготовить точный снимок `main`, входов, весов и собственный образ эксперимента. Записать digest образов, версии Python/пакетов, gateway и моделей в закрытый `environment-dir`. До первого исправления получить и проверить аутентифицированный gateway manifest, сохранив его снимок вне репозитория. Входы, веса и секреты монтировать только из личной области; кэши держать на SSD вне контейнера.
2. Выполнить `prepare` на закреплённых входах и сохранить новый `input_manifest-*.json` со схемой `det-rep-ec-r-v1`. CLI проверяет зафиксированные входные SHA-256 и хеш 750 ID. Для этого прогона использовать отдельные `work-dir`, `relation-dir` и `run-dir`; научный кэш изолирован в `work-dir/cache/ec-veriscore-r750-v1`.
3. Выполнить `extract-r` для всех 750 ID с точными `--manifest`, `--config`, `--embedding-path`, `--gateway-url`, `--work-dir`, `--relation-dir`. Затем запустить `verify-r` с теми же входами, `--manifest`, `--work-dir` и `--relation-dir` без модельных вызовов. Требуются `completed_sources=750`, `answer_graphs=750`, `failed=0`; данные и тройки остаются закрытыми. Опция `--gateway-manifest /path/to/frozen.json` закрепляет предварительно проверенный манифест. При разрешённой поэтапной проверке можно начать с `--max-sources 1`, затем продолжить тот же каталог без флага.
4. Выполнить `run` для тех же 750 ID и четырёх условий с теми же параметрами плюс `--run-dir`, `--vllm-url`, `--checkpoint`. CLI до preflight vLLM проверяет полный R-этап и идентичность его конфигурации. E использует KG-кэш только на чтение; C работает через VeriScore и четырёхклассовый Gemini verifier. `--max-sources 1` разрешает поэтапное возобновление. При недоступном Gemini B может продолжиться, а сбои E/C записываются с типом. Продолжать только при неизменной идентичности и в пределах отдельного разрешения владельца.
5. Выполнить `replay`. Выпускать архив только когда R имеет 750/750 артефактов без итоговых сбоев, `run_summary.json` показывает `completed=3000`, `failed=0`, а `replay_summary.json` — `expected=3000`, `completed=3000`, `missing=0`.
6. Выполнить `package-export` с `--relation-dir`, `--run-dir`, `--work-dir`, `--sources`, `--answers`, `--manifest`, `--repo-dir`, `--config`, `--environment-dir`, `--out-dir`. Проверить 3000 строк закрытой карты вариантов, целостность checksums и фактическое число уникальных слепых заданий. Дубли одинаковых итоговых ответов не добавлять искусственно.

Эти стадии — инструкция для **будущего разрешённого** запуска; подготовка репозитория не исполняет ни одну из них на сервере.

Для `package-export --repo-dir` нужен полный замороженный снимок кода: `.gcloudignore`, `.gitignore`, `.dockerignore`, `AGENTS.md`, `Dockerfile`, `Dockerfile.experiment`, `README.md`, `config.example.yaml`, `pyproject.toml`, `requirements-gateway.txt`, `gemini_recipient.py` и целиком каталоги `det_rep/`, `gemini_gateway/`, `scripts/`, `docs/`, `tests/`. Упаковщик отклоняет неполный снимок. Список `rsync` в [исторической инструкции QA100](history/qa100-20260919.md) для нового протокола неполон; при будущей разрешённой передаче сверять состав именно с этим списком.

## Снимок окружения для архива

`package-export` требует отдельный закрытый `environment-dir` с четырьмя непустыми файлами. Заполнить его по фактически запущенным контейнерам и закреплённому `run-dir` после разрешённого запуска, без секретов:

```text
environment-dir/
  container-image.json
  model-manifest.json
  python-packages.txt
  os-packages.txt
```

`container-image.json` содержит полный ID объединённого образа и digest закреплённого базового образа vLLM:

```json
{
  "experiment_image_id": "sha256:<actual experiment image ID>",
  "vllm_image_digest": "sha256:<actual vLLM image digest>"
}
```

`model-manifest.json` имеет вид:

```json
{
  "llama_checkpoint": "<runtime_config.json: corrector.checkpoint>",
  "embedding_revision": "<runtime_config.json: embedding_revision>",
  "gateway_manifest_sha256": "<det_rep.util.digest(contents of run-dir/gateway_manifest.json)>"
}
```

Заменить значения в угловых скобках фактическими строками: упаковщик проверяет точное совпадение трёх полей с закреплённым runtime и gateway manifest. Хеш gateway вычисляется функцией `det_rep.util.digest` от разобранного JSON, а не как SHA-256 байтов файла. В `python-packages.txt` сохранить список установленных Python-пакетов из экспериментального контейнера, в `os-packages.txt` — список пакетов его базовой ОС. Эти файлы нужны для воспроизводимости; пустой файл или отсутствующее поле останавливает упаковку.

## Передача результатов

`package-export` создаёт два логически раздельных пакета. **Закрытый пакет владельца** содержит точные входы и все 750 ID, снимок кода и окружения, конфигурацию/модели, 750 R-артефактов, evidence, feedback и научные кэши, все 3000 траекторий и хеши промптов, сбои, результаты `replay`, карту `source_id`/условий/`request_id`, provenance и контрольные суммы. Его доступ ограничен владельцем эксперимента.

**Слепой пакет для команды оценки** содержит все уникальные запросы с непрозрачным `request_id`, контекстом, вопросом, исходным и исправленным ответами и описание формата. Он не содержит `source_id`, название условия, R-тройки, диагностику E/C, кэши или приватную карту соответствий. Число строк определяется только фактической дедупликацией и может быть меньше 3000. Команда оценки отдельно строит evaluator и проводит ручной аудит; этот репозиторий лишь готовит коррекции и пакет данных.
