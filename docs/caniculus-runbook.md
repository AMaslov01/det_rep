# E/C-коррекция на caniculus

**Статус: подготовка, новый прогон не запущен.** Эта процедура относится к 100 исходным ID и четырём условиям `B`, `E`, `C`, `EC`. Прежний QA100 с 12 условиями завершён и описан отдельно в [исторической записи](history/qa100-20260919.md). Его разрешение на серверный запуск и возобновление не распространяется на новый прогон. Перед планированием передачи файлов, Docker, GPU или запуска сначала прочитать [правила сервера](server-resource-rules.md); для исполнения нужна отдельная команда владельца.

## Зафиксированный дизайн

- Выборка — ровно те же 100 доступных train `source_id`, что и в QA100: детерминированный отбор `smoke` (ровно 100 ID), по 50 каждой исходной CSV-метки. Метки GPT-4o используются здесь только для выбора сбалансированной выборки, не для оценки исправлений. CLI закрепляет SHA-256 точных снимков source JSONL и answer CSV, а `smoke` до модельного preflight проверяет хеш выбранных 100 ID; при несовпадении выполнение останавливается.
- Каждый ответ независимо исправляется с исходного текста за одну итерацию: `B` видит вопрос, evidence и ответ; `E` дополнительно видит диагностику сущностей; `C` — клеймы VeriScore с четырёхклассовой проверкой Gemini (`veriscore.claim_verifier.labels: critical`, настройки `critical.claim_verifier`, протокол кэша `det-rep-four-way-verdict-v1`); `EC` — оба блока. VeriScore-клеймы не отбираются по наличию entity. Компоненты `R` и `X` в эксперименте отсутствуют.
- Все условия используют одинаковые исходные данные, evidence, Llama checkpoint, параметры генерации и prompt-основу. Gemini готовит только нужные E и C отдельно; сбой одного компонента фиксируется с типом и не превращается в успешный результат другого. `B` не требует Gemini.
- Ожидаемый объём полного прогона — **100 × 4 = 400 траекторий**. Ни код, ни запуск не вычисляют оценку качества исправлений. Независимый evaluator и ручной аудит принадлежат другой команде.

## Подготовка отдельного запуска

Новый run-dir и кэши разместить вне репозитория в личной области `/mnt/ssd/a.maslov` с закрытыми правами. Не использовать каталог, кэши или результаты `qa100-20260919` как результаты E/C. Входные `source_info.jsonl` и CSV, полный input manifest, код/образ, `config.example.yaml`, Gemini gateway revision, снимок S-BERT и точный commit весов Llama должны быть проверены и закреплены до первого запроса. Изменение любого из них, seed, числа итераций или списка условий требует нового каталога запуска; возобновлять можно только неизменный запуск.

На caniculus научный Python исполняется только в Docker без root. GPU 2 передаётся по её актуально проверенному UUID только контейнеру vLLM. Перед запуском повторно проверить владельца рабочей области, свободное место, Docker, загрузку GPU и процессы; согласовать время и предупредить коллег согласно [правилам](server-resource-rules.md). Контрольные версии и UUID, записанные в сентябре, могут измениться; их значения в [истории QA100](history/qa100-20260919.md) не заменяют новую проверку. Не затрагивать чужие файлы, контейнеры или процессы.

Когда владелец отдельно разрешит запуск, выполнить стадии по порядку:

1. Подготовить точный снимок `main`, входов, весов и собственный образ эксперимента. Записать digest образов, версии Python/пакетов, gateway и моделей в закрытый `environment-dir`. До первого исправления получить и проверить аутентифицированный gateway manifest, сохранив его снимок вне репозитория. Входы, веса и секреты монтировать только из личной области; кэши держать на SSD вне контейнера.
2. Выполнить `prepare` на закреплённых входах и сохранить новый `input_manifest-*.json` со схемой `det-rep-ec-v1`; манифест QA100 с другой схемой не переиспользовать. CLI сам проверяет зафиксированные входные SHA-256 и хеш 100 ID; новая `run_identity.json` должна закреплять `B,E,C,EC` и одну итерацию. Для этого прогона использовать отдельные `work-dir` и run-dir; научный кэш изолирован в `work-dir/cache/ec-veriscore-v1`.
3. Запустить коррекцию в Docker с `smoke` (CLI фиксирует 100 ID и одну итерацию), точными `--manifest`, `--config`, `--embedding-path`, `--checkpoint`, `--gateway-url`, `--vllm-url`, `--work-dir` и `--run-dir`. При отдельно разрешённой поэтапной проверке можно начать с `--max-sources 1` и затем продолжить тот же каталог без этого флага. Опция `--gateway-manifest /path/to/frozen.json` закрепляет предварительно проверенный манифест без живого запроса; при возобновлении CLI берёт `gateway_manifest.json` из run-dir и отклоняет конфликтующий снимок. При недоступном Gemini условие B может продолжиться, а сбои E/C записываются с типом. При сбое изучать собственные `failures/` и продолжать только при неизменной идентичности прогона и в пределах разрешённого владельцем восстановления.
4. Выполнить `replay` на том же закреплённом наборе. Выпускать архив только когда `run_summary.json` показывает `completed=400`, `failed=0`, а `replay_summary.json` — `expected=400`, `completed=400`, `missing=0`.
5. Выполнить `package-export` с `--run-dir`, `--work-dir`, `--sources`, `--answers`, `--manifest`, `--repo-dir`, `--config`, `--environment-dir`, `--out-dir`. Проверить 400 строк закрытой карты вариантов, целостность checksums и фактическое число уникальных слепых заданий. Дубли одинаковых итоговых ответов не добавлять искусственно.

Эти стадии — инструкция для **будущего разрешённого** запуска; подготовка репозитория не исполняет ни одну из них на сервере.

Для `package-export --repo-dir` нужен полный замороженный снимок кода: `.gcloudignore`, `.gitignore`, `.dockerignore`, `AGENTS.md`, `Dockerfile`, `Dockerfile.experiment`, `README.md`, `config.example.yaml`, `pyproject.toml`, `requirements-gateway.txt`, `gemini_recipient.py` и целиком каталоги `det_rep/`, `gemini_gateway/`, `scripts/`, `docs/`, `tests/`. Упаковщик отклоняет неполный снимок. Список `rsync` в [исторической инструкции QA100](history/qa100-20260919.md) для нового протокола неполон; при будущей разрешённой передаче сверять состав именно с этим списком.

## Снимок окружения для архива

`package-export` требует отдельный закрытый `environment-dir` с четырьмя непустыми файлами. Заполнить его по фактически запущенным контейнерам и закреплённому `run-dir` после разрешённого запуска, без секретов:

```text
environment-dir/
  container-image.json
  model-manifest.json
  python-packages.txt
  os-packages.txt
```

`container-image.json` содержит полный ID образа научного контейнера и digest точного образа vLLM:

```json
{
  "experiment_image_id": "sha256:<actual experiment image ID>",
  "vllm_image_digest": "sha256:<actual vLLM image digest>"
}
```

`model-manifest.json` имеет вид:

```json
{
  "llama_checkpoint": "<runtime_config.json: corrector.checkpoint>",
  "embedding_revision": "<runtime_config.json: embedding_revision>",
  "gateway_manifest_sha256": "<det_rep.util.digest(contents of run-dir/gateway_manifest.json)>"
}
```

Заменить значения в угловых скобках фактическими строками: упаковщик проверяет точное совпадение трёх полей с закреплённым runtime и gateway manifest. Хеш gateway вычисляется функцией `det_rep.util.digest` от разобранного JSON, а не как SHA-256 байтов файла. В `python-packages.txt` сохранить список установленных Python-пакетов из экспериментального контейнера, в `os-packages.txt` — список пакетов его базовой ОС. Эти файлы нужны для воспроизводимости; пустой файл или отсутствующее поле останавливает упаковку.

## Передача результатов

`package-export` создаёт два логически раздельных пакета. **Закрытый пакет владельца** содержит точные входы и выбранные ID, снимок кода и окружения, конфигурацию/модели, evidence, feedback и научные кэши, все траектории и хеши промптов, сбои, результаты `replay`, карту `source_id`/условий/`request_id`, provenance и контрольные суммы. Его доступ ограничен владельцем эксперимента.

**Слепой пакет для команды оценки** содержит все уникальные запросы с непрозрачным `request_id`, контекстом, вопросом, исходным и исправленным ответами и описание формата. Он не содержит `source_id`, название условия, диагностику E/C, кэши или приватную карту соответствий. Число строк определяется только фактической дедупликацией и может быть меньше 400. Команда оценки отдельно строит evaluator и проводит ручной аудит; этот репозиторий лишь готовит коррекции и пакет данных.
